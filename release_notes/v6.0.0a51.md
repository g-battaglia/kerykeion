# v6.0.0a51

## Void-of-Course Moon: correct `next_aspect`

This alpha fixes `VoidOfCourseMoonFactory` / `VoidOfCourseMoonModel.next_aspect`.
It now reports the Moon's **first exact aspect after it ingresses into the next
sign** — the aspect that ends the void-of-course lull — instead of an event taken
from the current sign.

## The bug

`compute_void_of_course` enumerated only the aspects the Moon makes *within the
current sign* and picked `next_aspect` from that same list. When the queried
moment fell before the last in-sign aspect, that aspect was simultaneously
`last_aspect` (the latest in-sign aspect, which starts the void) and `next_aspect`
(the next future aspect in the list) — so the two fields were identical.

## The fix

`next_aspect` is now sought with a dedicated scan of the **next** sign: after
computing the ingress, a second `_aspects_in_window` pass runs between the ingress
and the following sign cusp (seeded from the midpoint of that sign), and its first
event becomes `next_aspect`. `last_aspect` and `next_aspect` therefore always live
in different signs and can never coincide.

```python
from kerykeion import VoidOfCourseMoonFactory

voc = VoidOfCourseMoonFactory.from_datetime(2026, 5, 29, 12, 0, tz_str="Europe/Rome")
voc.last_aspect   # last aspect in the current sign (starts the void)
voc.next_aspect   # first aspect in the next sign (ends the void lull) — distinct
```

## Semantics change

`next_aspect` is no longer `None` while the Moon is void: it now points at the
first aspect of the next sign in every realistic case (`None` only in the
degenerate event the Moon makes no aspect at all while traversing that sign, which
effectively never happens). The field stays `Optional` with the same type;
`last_aspect`, the void window, and `is_void_of_course` are unchanged.

## Implementation notes

- Pure refactor of `compute_void_of_course`: the in-sign enumeration was extracted
  into a reusable `_aspects_in_window(jd_ref, win_start, win_end, iflag)` helper,
  called once for the current sign and once for the next. The Newton/seed engine,
  `EPHEMERIS_LOCK` usage and ephemeris backend are unchanged (no swisseph-specific
  code path; only the active backend).
- Cost is ~2× single-body position lookups (still a few dozen); no full
  astrological subject is ever built.
