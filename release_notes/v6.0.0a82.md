# v6.0.0a82 — The orb matrix: per-point adjustments learn the aspect

This alpha extends `point_orb_adjustments` — the per-point orb adjustment
table — so an entry can vary **by aspect**. No default changes anywhere: a
request that does not use the new form computes byte-identical charts.

## What changed

A table entry used to be a single number, an additive delta applied to every
aspect's base orb when that point is involved. It can now also be a mapping
of aspect name → delta, with `"*"` as the default for aspects not listed:

```python
point_orb_adjustments={
    "Sun": {"*": 1.5, "conjunction": 3.0},  # 3.0° on Sun conjunctions, 1.5° elsewhere
    "Moon": 1.5,                            # number ≡ {"*": number}
    "Ascendant": {"conjunction": -3.0},     # configured ONLY for conjunctions
}
```

Lookup per (point, aspect) is `map[aspect] ?? map["*"] ?? absent`. The
explicit-only rule that has always governed this table — a missing point is
*not* treated as `0.0`, which is what makes negative (tightening) deltas
work — carries over per aspect: without `"*"`, a point is unconfigured for
the aspects it does not list, so a negative delta on the other endpoint
keeps tightening those pairs. The equivalence `number ≡ {"*": number}` is
strict, down to the error contract: malformed values raise identically on
both forms.

The combination strategies (`max_explicit`, `min_explicit`, `sum`, `none`)
are untouched as a concept — they now operate on the two per-aspect resolved
values of the pair.

## Where it works

Everywhere the table already worked: `AspectsFactory.single_chart_aspects`
and `dual_chart_aspects`, every `ChartDataFactory` chart type,
`SecondaryProgressionFactory.compute_full` and `SolarArcFactory.compute`.
The solar-arc self-conjunction guard now sizes itself to the conjunction's
own delta (resolved independently of the aspect filter, only for same-name
pairs) and clamps the whole sum at zero exactly like detection does. Both
predictive entry points validate the full adjustment table up front, closing
a gap where a typo'd aspect key or a non-finite leaf outside the selected
aspects passed silently.

## API surface

- `resolve_pair_orb_adjustment` gains a keyword-only `aspect_name` parameter
  (default `None` — every pre-existing caller keeps its exact behavior:
  aspect-keyed entries resolve through `"*"` only).
- New helpers in `kerykeion.aspects.orb_utils`: `lookup_point_adjustment`,
  `has_aspect_keyed_adjustments`, `resolve_pair_orb_adjustments_for_aspects`.
- `get_aspect_from_two_points` accepts a per-aspect `extra_orb` mapping; the
  scalar fast path is byte-identical to before, and the per-aspect path only
  activates when a table actually contains a mapping entry.
- Validation stays permissive where the ecosystem is permissive: an unknown
  aspect name in a mapping logs a warning (it can never match) but does not
  raise, mirroring `active_aspects`; non-finite leaves are rejected up front.

## Compatibility

Every existing `point_orb_adjustments` value is valid unchanged and resolves
identically. No golden fixture moved. Callers that never pass the map form
are unaffected in behavior and in performance.
