# v6.0.0a50

## Twilight in SunTimesFactory

This alpha adds **civil, nautical and astronomical twilight** to
`SunTimesFactory` / `SunTimesModel`, alongside the existing sunrise, sunset,
solar noon and day length.

## What's new

### Six new `SunTimesModel` fields

```python
from kerykeion import SunTimesFactory

sun = SunTimesFactory.from_date(2026, 5, 28, latitude=41.9028,
                                longitude=12.4964, tz_str="Europe/Rome")
sun.civil_dawn, sun.civil_dusk                # Sun at -6 degrees
sun.nautical_dawn, sun.nautical_dusk          # Sun at -12 degrees
sun.astronomical_dawn, sun.astronomical_dusk  # Sun at -18 degrees
```

Each field is an optional timezone-aware UTC `datetime`. Dawn is the morning
(ascending) crossing, dusk the evening (descending) one.

## Implementation notes

- Computed by the new `compute_twilight_events`, which drives the active
  ephemeris backend's `rise_trans` twilight bits (`BIT_CIVIL_TWILIGHT` /
  `BIT_NAUTIC_TWILIGHT` / `BIT_ASTRO_TWILIGHT`, geometric — no refraction),
  reusing the existing Julian-Day / `EPHEMERIS_LOCK` infrastructure. No
  swisseph-specific code paths.
- Dawn is sought from local midnight, dusk from local noon so it is the evening
  crossing (dawn < dusk, a monotonic civil → nautical → astronomical run). Like
  the paired sunset, an evening dusk can land in the small hours of the next
  civil date.
- A field is `None` when that twilight does not occur — polar day, or a
  high-latitude summer where the Sun never sinks to the angle. During polar
  *night* the deeper nautical/astronomical twilight can still be present while
  civil is `None`. Circumpolar backend errors degrade to `None` rather than
  propagating.

## Backward compatibility

Fully additive — the six fields default to `None`; no existing behavior, model
or signature changes.
