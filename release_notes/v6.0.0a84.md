# v6.0.0a84 — One package per domain, and a visible v5 upgrade path

This alpha is structural. **No calculation changed, and no public name moved:**
`kerykeion.__all__` exports exactly what a83 exported, and the JSON schema of
every Pydantic model among them is byte-identical to a83. Serialized output is
unchanged.

What changed is where the code lives, plus two things that were breaking
quietly and now do not.

## One file at the package root

`kerykeion/` was organised two ways at once: 33 domains lived in packages with a
re-exporting `__init__.py`, while 16 modules — often the largest in the library —
sat as single files in the root. Naming inside the packages was split too:
`firdaria/factory.py` next to `eclipses/eclipse_factory.py`.

Now `kerykeion/__init__.py` is the only `.py` file in the package root, and every
domain is a directory with a uniform internal rule:

1. The package is the domain, the file is the role: `X_factory.py` → `X/factory.py`.
2. Inside a package, no prefix repeating the package name.
3. `factory.py` is reserved for the factory the package is named after; a second
   technique keeps its own domain name (`secondary_progressions/solar_arc.py`).
4. Nothing else is renamed. `orb_utils.py`, `config_constants.py`, `rulers.py`,
   `catalog.py`, `nakshatra_*.py` and `draw_*.py` keep their names, because their
   prefix is a real distinction rather than a repetition.

`kerykeion/kr_types/`, the v4-era shim deprecated throughout v5, is removed.
`setup.cfg` went with it: it configured flake8, which is not among the project's
gates, and named a file that no longer exists.

### Does this affect your code?

**If you import from the top level — `from kerykeion import X` — nothing changes.**
That is the documented form and it is untouched.

If you imported a module directly, some paths moved. The migration guide now
carries the full v5 → v6 table; the most likely ones:

| v5 | v6 |
|:---|:---|
| `kerykeion.charts.chart_drawer` | `kerykeion.charts.drawer` |
| `kerykeion.schemas.kr_models` | `kerykeion.schemas.models` |
| `kerykeion.schemas.kr_literals` | `kerykeion.schemas.literals` |
| `kerykeion.astrological_subject_factory` | `kerykeion.astrological_subject.factory` |
| `kerykeion.chart_data_factory` | `kerykeion.chart_data.factory` |
| `kerykeion.planetary_return_factory` | `kerykeion.planetary_returns.factory` |

`kerykeion.report`, `kerykeion.utilities`, `kerykeion.ephemeris_backend`,
`kerykeion.motion` and `kerykeion.swisseph_setup` became packages under the same
name, so imports from them keep working — including the names they merely
re-exported, which are pinned by a test so a future move cannot drop them
silently.

`python -m kerykeion.swisseph_setup` still works and prints the same `--help`.

## The silent half of the v5 upgrade

Upgrading from v5 breaks in two ways, and only one is loud. The removed v5 API
(`AstrologicalSubject`, `KerykeionChartSVG`, `NatalAspects`, `SynastryAspects`)
raises an `ImportError` naming its replacement — that case announces itself.

The quiet one hits the users who **had already migrated correctly**: v6 changed
defaults that alter results, so code written against the v5 factory API keeps
running and returns different numbers. Nothing raises, nothing warns.

- **Active points: 18 → 14.** `Descendant`, `Imum_Coeli`, `True_South_Lunar_Node`
  and `Mean_Lilith` are no longer computed unless requested.
- **Aspect orbs are narrower.** Conjunction and opposition went from 10° to 6°,
  trine from 8° to 6°, and quintile left the defaults entirely.
- **Non-natal charts use a flat 3°.** Transits, returns and progressions route
  through `PREDICTIVE_ACTIVE_ASPECTS`. On one sample chart that is 19 transit
  aspects against 51 under v5 orbs — the natal difference is small, this one is not.
- **Chart style: `classic` → `modern`,** which also changes the saved filename.

Three changes make this visible instead of silent:

1. The removed-name `ImportError` now names the changed defaults too — it is the
   one moment we know the reader is looking.
2. `kerykeion.settings.V5_DEFAULT_ACTIVE_POINTS` restores the old point set
   explicitly. It is a frozen historical record, not a maintained preset: it will
   not follow future changes to the defaults.
3. The migration guide gained a **"What changes in the results"** section with
   runnable examples for all four, including the v5 aspect list and
   `style="classic"`.

There is deliberately **no compatibility wrapper** for the removed v5 classes.
With the defaults staying breaking, a wrapper would remove the signal without
removing the change: the code would run and the results would still differ, and
the `DeprecationWarning` meant to compensate is hidden by default in Python
unless the call sits in `__main__`.

## A structural gate

`scripts/check_import_graph.py` (wired into `poe check`) covers what mypy and
pyright cannot: they only look at `kerykeion/`, so the ~1500 module paths written
in `tests/`, `scripts/` and `examples/` were unchecked — and the ones written
*inside strings* were invisible to every existing tool.

Four modes, each aimed at a failure that otherwise stays silent: `--paths`,
`--patch-targets`, `--loggers`, `--fresh-imports`. Between them they caught, on
this branch alone, seven `caplog` filters left pointing at a package, five tests
patching through a stale module alias, and a test that passed even when its
subprocess died of `ImportError`.

## Other fixes

- `SIGN_CODES` is exported from `kerykeion.schemas`, so the constant no longer
  requires a private module path.
- `DEFAULT_ACTIVE_POINTS`, `DEFAULT_ACTIVE_ASPECTS` and `ALL_ACTIVE_POINTS` are
  re-exported from `kerykeion.settings`, so callers can depend on the package
  facade rather than on `config_constants`' filename.
- The composite polar-fallback example in the docs called
  `CompositeSubjectFactory(polar_a, polar_b)` with neither name ever bound; both
  subjects are now defined and the snippet runs.

## Compatibility

Requires `libephemeris>=3.1.0,<4` and Python 3.12+, unchanged from a83.
